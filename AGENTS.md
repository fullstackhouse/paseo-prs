# paseo-prs

Paseo plugin: one composer pill per agent for the PRs related to its workspace (branch PRs ∪ their stack ∪ linked PRs); Create PR when none.

## Layout

- `server/autolink.ts`: links the PRs an agent opened (`gh pr create` output, `create_pull_request` MCP results) to its workspace on `agent.turn_ended`, reading only that turn's items so a PR the human unlinked stays unlinked.
- `shared/prs.ts`: Zod schemas, RPCs (`prs.list`, `prs.link`, `prs.unlink`), `parsePrRef` (URL / `o/r#1` / `#1`), `parseRemote`, `stackOf` (base/head walk down and up), `relatedPrs` (merge by URL), `pillFor` (pure: branch + linked → one pill spec), `rowDetail`, agent prompts (Create PR asks Paseo for its prompt via `workspaces.ref(id).pullRequestPrompt()`). All logic worth testing lives here or in pure server modules.
- `server/github.ts`: PR state comes from the host (`hostPrFetcher` → `paseo.changeRequests.read`, FSH hosts from fullstackhouse/paseo#270; typed locally in `server/host-sdk.ts`), which reads every plugin's PRs through one batched reader with one rate-limit pause and a 30 s cache. Older hosts lack it: reads fail with `PrReadsUnavailable` (logged once) and the rows show stale. `gh` only finds which PRs belong to a workspace: `readBranch(cwd)` via `git` + `gh pr list --head` (numbers only), and the stack from one `gh pr list --state open` (number/head/base only); `EdgeCache` (that open-PR list per repo, not per worktree); `BranchCache` (per cwd); `PrCache` (linked PRs by URL, reads only stale ones). TTL 2 min, 1 h for merged/closed PRs, unless forced; `PrCache` never rereads a linked PR once it's merged, even forced (a forced refresh follows every turn, and track workspaces link dozens of merged PRs). Every gh call goes through `Gh`, which pauses all of them once GitHub reports a rate limit (until the GraphQL reset, else 5 min) while the caches serve what they have.
- `server/store.ts`: `LinkStore`, `links.json` in `~/.paseo/plugin-data/prs` (`PASEO_PRS_DIR` overrides). `server/links.ts`: link/unlink/list shared by RPCs and MCP; links only PRs GitHub returns, under GitHub's repo spelling. While PRs can't be read (host paused GitHub reads, or unreachable) it links them as given and marks them stale instead of rejecting them: auto-link and agents link PRs they just opened and have no second chance.
- `server/fork.ts`: `forkIntoPr` (agent create with `worktree: checkout-pr`, source config, `github_pr` + `chat_history` attachments, labels `prs.forkedFrom`/`prs.pr`, no `parent`); `chatHistoryText` rebuilds core's chat history from the timeline because `buildAgentForkContext` is not on the plugin SDK's `PaseoApi`. `shared/prs.ts` `prAgentFor` (Open instead of a duplicate fork) and `canFork`.
- `server/reports.ts`: a fork's report to its main chat. `Reports.start` (the Done button, RPC `prs.report`) records a pending report with the prompt it sends; `turnEnded` refetches the fork's timeline and forwards `replyTo` (the reply after that prompt, since it was sent) via `send(…, { sourceAgentId, activeTurnBehavior: "steer" })`. Nothing else messages the main agent. `ReportStore`: `reports.json`, exposed by `prs.reports`. `shared/prs.ts`: `reportPrompt`, `reportMessage`, `reportPillFor`, `reportButton`. `client/ReportPopover.tsx`: the fork's popover.
- `server/bridge.ts` + `server/listener.ts` (copied from paseo-asks): stdio MCP script → localhost HTTP. `server/tools.ts`: `prs_link`/`prs_unlink`/`prs_list`, `pickCaller` (Codex has no `PASEO_AGENT_ID`), permission matcher.
- `client/summary.ts`: one workspace summary item (`prs`) per workspace for the FSH host's Overview: `pullRequests` (`summaryState`/`overviewPr`: every related PR, the pill's `prStatus` as `facts`, `repo` name only for a foreign repo, capped at 50) and `pullRequestsStale` (a `stale` branch or links read, or `prs.list` failing). Always `entries: []`, never `needsYou`/`status`. Typed locally under `COMPAT(workspaceSummaryItem)`, a no-op on hosts without `addWorkspaceSummaryItem`. `BranchCache` and `PrCache` mark what they serve from a failed read as stale.
- `client/pills.ts`: subscribes to agents, one pill per agent (`update` only the face; a new `behavior` closes an open popover). Forced refresh when an agent goes running → idle; 60 s poll otherwise. `client/PrsPopover.tsx`: the list, link field, unlink ×, prompt buttons (disabled while the agent runs; `send()` interrupts a turn). `client/inbox.ts`: the Review button's `navigation.openPluginScreen` call into paseo-inbox's `review` screen with `{ pr: url }` and the popover's `workspaceId`, so it opens as a tab there (FSH hosts only, typed locally until the SDK has it). `client/OpenAgentScreen.tsx`: popovers get no `navigation` on 0.12 hosts, so Open/Fork go through this screen, which calls `navigation.openAgent`. `index.client.tsx`: `/link-pr`, the screen.

## Load-bearing facts (Paseo 0.12)

- Composer pills are imperative registrations from the client entry, not components; `client.rpc` is available there. Popover content gets no `navigation`.
- Menus can't hold inputs, hence the popover.
- `tsconfig.json` needs `"react-native"` in `types` for `setInterval`/`AbortController`/`console` in a `.ts` client file.
- The plugin subprocess may lack the shell PATH; `server/github.ts` appends Homebrew paths.
- MCP tools are injected in `before("agent.create")` with `toolPolicy.preapproved`; plan mode and Codex still prompt, so `agent.permission_requested` allows `mcp__prs__*`.
- checkout-pr worktrees get a local branch that may differ from the PR head (`feat/x-1` tracking `origin/feat/x`); `readBranch` lists PRs by the upstream branch.
- Fork with the resolved model (`runtimeInfo.model`, e.g. `claude-haiku-5-5`), not the snapshot's alias (`haiku`), or the new agent loses its thinking options.
- Agent-to-agent messages are core's: a plugin `send` with `sourceAgentId` gets the same envelope and queue as `send_agent_prompt`. Omitting `activeTurnBehavior` interrupts a running turn. Forks have no `parent`: core would report every finished turn of a child to it.
- `agent.turn_ended` can arrive with an empty `timeline`, even for the turn that answered; refetch the timeline, and match the reply to the prompt and its send time (an identical earlier prompt has a stale reply).

## Commands

- `npm run typecheck`, `npm test`.
- After edits: `paseo plugin reload paseo-prs`, then `paseo plugin ls` must say `running`; logs via `paseo plugin logs paseo-prs`. Never restart the daemon.
- UI check without the daemon password: run a sandbox daemon (`paseo daemon run --home /tmp/x`, `config.json` with `pluginsEnabled: true` and `daemon.cors.allowedOrigins: ["http://127.0.0.1:6767"]`), install the plugin with `--home`, then direct-connect the web app at `http://127.0.0.1:6767` to it.
